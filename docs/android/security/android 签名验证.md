# Android APK 防重打包校验分析与绕过

> 用于自有应用、教学样本或明确授权的 APK 安全分析。本文重点是应用内的防重打包自检，帮助定位校验逻辑、理解常见实现并在测试样本中验证其效果。

## 1. 先区分系统校验与应用自检

### Android 系统的 APK 签名校验

Android Package Manager 在安装 APK 时验证签名；更新已有应用时，还会检查新旧包的签名身份是否兼容。重新签名的 APK 通常不能直接覆盖安装到原签名的应用上。APK Signature Scheme v1、v2、v3 由系统安装流程验证；v3 支持签名密钥轮换，v4 为增量安装提供配套的 `.idsig` 文件。

这是平台安装规则。应用里的普通 Java / Kotlin 校验代码不能改变 Package Manager 的安装判断。

### 应用内的防重打包自检

应用可以读取自身签名证书，与发布时保存的预期证书或 SHA-256 指纹比较。若不匹配，应用可能退出、限制功能、提示风险，或向服务端报告完整性异常。本文提纲中的三种情况——比较摘要字符串、比较 DER 字节、只比较布尔值——都属于这类本地校验实现。

应用内自检和系统安装校验是两层机制。分析时要先确认目标是哪一层，不能把“应用检测到重签名”说成“伪造了原始签名”。

## 2. 证书与比较对象

- **签名证书：**包含公钥和证书信息，可用于识别签名者；证书不是秘密。
- **证书 DER：**证书的二进制编码。Android 的 `Signature.toByteArray()` 可取得相应编码。
- **证书 SHA-256 指纹：**对证书 DER 计算 SHA-256 的结果。它不是 APK 文件哈希，也不是 APK 签名块的原始字节。
- **签名私钥：**发布方用来签名 APK 的秘密材料，不应包含在 APK 中。

从 APK 提取到证书或指纹很正常；这不等于取得了签名私钥，也不能据此生成与原发布者相同的签名。

## 3. 定位自检代码

先从“取证书”追到“比较结果”再追到“限制行为”，不要只凭某个 API 名称下结论。

### 常见取证书入口

- `PackageManager.getPackageInfo()`
- `PackageInfo.signatures` 与旧标记 `GET_SIGNATURES`
- `PackageInfo.signingInfo`、`SigningInfo.apkContentsSigners`
- `SigningInfo.signingCertificateHistory`
- `PackageManager.hasSigningCertificate()`
- 获取 `context.packageName`、硬编码包名或其他目标包名的代码

### 常见摘要与比较点

- 摘要：`MessageDigest`、`SHA-256`、`SHA-1`、`MD5`
- 格式转换：Hex、Base64、大小写转换、冒号和空格处理
- DER / 字节比较：`Signature.toByteArray()`、`Arrays.equals()`、`MessageDigest.isEqual()`
- 结果门控：`isSignatureValid()`、`checkSign()` 一类封装函数，以及其调用方的 `if` 分支、退出逻辑或功能开关

典型数据流如下：

```text
PackageManager 取得当前证书
        ↓
选择当前签名者或签名历史
        ↓
计算指纹 / 取得 DER 字节
        ↓
与预期值比较，生成 true 或 false
        ↓
调用方决定继续、退出、限制功能或上报
```

关键问题是：比较的输入从哪里来、预期值是什么、结果流向哪里、失败时是否真的阻止了受保护操作。

## 4. 三类实现与测试思路

### A：比较摘要字符串

典型逻辑是对证书 DER 计算 SHA-256，转成十六进制或 Base64 文本，再与内置指纹比较。

分析时记录：摘要算法、被摘要的字节、格式转换规则、常量来源、字符串比较位置。大小写、冒号和空白会造成格式不一致；MD5 / SHA-1 不适合作为新的证书指纹方案。不要只搜索硬编码字符串，预期值也可能拆分、编码或由资源加载。

在授权测试样本中，可以使用测试签名构建验证“证书变化是否触发预期失败路径”，再通过受控的动态分析确认最终决策是否只依赖这一处本地比较。绕过分析关注的是本地比较结果和调用方分支是否可被控制，不是尝试伪造 SHA-256 或恢复发布私钥。

### B：比较签名证书 DER 字节

典型逻辑是把当前签名证书的 DER 字节与内置证书字节进行全量比较。

分析时确认：两边是否确实都是证书 DER；比较是逐字节精确匹配，还是先做了截断、编码或摘要；多签名者场景采用“任意一个匹配”还是“全部匹配”。直接比较 DER 避免了指纹文本格式问题，但不会让客户端的比较逻辑免于静态修改或运行时控制。

测试时同样先用不同测试证书触发不匹配，再追踪比较结果如何影响功能。若 DER 比较和其后的失败分支都在客户端，攻击面仍是这段本地决策逻辑；DER 更长并不构成额外的信任边界。

### C：只比较布尔值

代码可能直接调用 `hasSigningCertificate()`，也可能把复杂检查封装到返回 `Boolean` 的函数中。调用处只看到 `true / false`，并不能说明校验是否正确。

沿调用链检查：布尔值由哪个包和证书产生；是否考虑签名轮换和多签名者；异常或空结果是否默认放行；有多少调用点依赖这个结果。授权动态测试可以验证改变本地检查结论后，哪些界面或操作随之变化，并进一步确认服务端是否仍会独立拒绝不可信请求。

若测试中“让校验通过”就能进入受保护流程，说明该流程依赖可控的客户端判断。报告时应写清楚本地影响和服务端影响；不要仅凭布尔值可被改变就推断服务器授权也已被绕过。

## 5. 签名轮换和 Android API 细节

Android 9（API 28）及以上可使用 `PackageManager.hasSigningCertificate()`。使用 `CERT_INPUT_SHA256` 时，参数应是 SHA-256 的原始 32 字节摘要，而不是十六进制字符串的 ASCII 字节。

`SigningInfo.apkContentsSigners` 表示当前 APK 的签名者；`signingCertificateHistory` 用于查看单签名者的证书沿袭历史。密钥轮换后，旧证书出现在可信历史中与它仍是当前签名者不是一回事。多签名者也有不同语义。分析时应按应用的发布策略判断接受集合，不要简单地把“历史上出现过”视为永远可信。

`GET_SIGNATURES` 已弃用。API 28 及以上优先检查 `SigningInfo` 或 `hasSigningCertificate()`；旧版本兼容分支也要纳入审计，因为不同 Android 版本可能走不同代码路径。

查看 APK 签名和证书指纹可用：

```text
apksigner verify --verbose --print-certs app.apk
```

确认检查的是正确 APK、构建变体和签名配置；debug、release 或不同分发渠道可能使用不同证书。

## 6. 授权样本的验证流程

1. **建立基线：**记录原始测试 APK 的版本、包名、签名指纹、设备 Android 版本和正常行为。
2. **触发检测：**使用自己的测试签名构建可控样本，确认应用内检查是否识别到证书变化，以及触发了哪条失败路径。
3. **追踪决策：**从证书读取点一路跟到比较、布尔结果、调用方和受保护功能，检查是否存在重复检查、延迟检查或 Native 实现。
4. **验证本地绕过边界：**在隔离测试环境对本地决策做受控动态验证，记录哪些客户端行为因此改变。这里只能证明本地逻辑可控，不能单独证明服务端接受了请求。
5. **验证服务端影响：**用测试账号和测试环境检查关键 API 是否仍由服务端进行身份认证、对象授权和业务规则校验。
6. **覆盖版本路径：**检查 Android 版本差异、密钥轮换、多渠道构建、冷启动和后续敏感操作是否使用同一套判断。

## 7. 常见误判与防护建议

- **把改动本地检查说成伪造签名。**本地分支或校验结果被控制，不等于拥有原签名私钥。
- **认为系统一定会阻止安装所有重签名 APK。**不同签名的 APK 不能作为原应用的正常更新；但用户可能在卸载原应用后安装另一个签名版本，具体还受安装来源和设备策略影响。
- **认为 DER 比较或混淆就不可绕过。**这些做法能增加分析成本，但校验和调用方仍运行在客户端控制范围内。
- **只看启动结果。**检查可能在特定页面、联网操作或后续流程才触发；要追踪实际保护的操作。
- **把本地绕过等同服务端越权。**服务端必须独立验证身份、资源权限、请求时效和关键业务状态。完整性证明（例如 Play Integrity）也应由服务端结合业务策略验证，不能只相信客户端上传的布尔值。
- **忽略误报与升级。**签名轮换、渠道证书变化和旧版本兼容都可能造成误拒；发布策略要明确允许哪些证书及沿袭关系。

## 8. 报告结论模板

> 应用通过【证书指纹 / DER / 系统布尔 API】实施客户端防重打包检查。检查位于【类 / 方法 / 调用链】，不匹配时会【实际失败行为】。在【测试版本与环境】中，受控改变本地校验决策可使【客户端行为】继续执行；服务端对【关键接口 / 业务操作】的独立校验结果为【结果】。因此影响范围是【仅客户端限制 / 服务端业务也受影响】，证据包括【日志、请求响应、代码路径或测试记录】。
