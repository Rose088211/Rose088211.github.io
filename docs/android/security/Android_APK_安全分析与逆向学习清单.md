# Android 安全分析 map.txt 解读与 APK 逆向检查清单

> 面向 Android 应用安全学习、代码审计和已获授权的测试。请只分析自有应用、教学样本或明确授权的目标；验证服务端行为时使用测试环境和测试账号。

本文分为两部分：先解释 `android map.txt` 的分类结构，再把 map 中的内容展开成可执行的检查清单。**分析对象限定为目标 APK**：可以分析 APK 的代码、配置、数据流、系统 API 使用和网络行为；不能仅凭 APK 分析挖掘 Android Framework、驱动或内核漏洞。map 是领域总览，不是严格互斥的分类树；实际分析时，一个问题可能同时涉及多个分析面和方法。

## 1. map.txt 的结构与逐项解读

分类时要分清三个不同维度：

| 维度 | 例子 | 回答的问题 |
| --- | --- | --- |
| 分析阶段或对象 | Manifest、代码、存储、网络、Native | 在看什么？ |
| 分析方法 | 静态、动态、协议分析 | 怎么看？ |
| 信任边界或安全要素 | 客户端、服务端、数据、密钥、算法 | 谁作出决定、保护什么？ |

因此，“本地验证 / 服务端验证”适合描述校验逻辑的位置；“静态 / 动态”描述分析方法；“数据 / 密钥 / 算法”描述检查对象。它们可以交叉标注，不宜硬塞进同一层级。很多应用同时包含客户端预检查和服务端最终裁决。

`android map.txt` 是一张领域地图，不是一棵每个节点都互斥的严格分类树。它把“保护状态”“分析面”“想验证的安全结果”和“分析方法”放在同一张图里，所以同一个问题会同时落到好几个分支。阅读时可把它理解成四个问题：

1. **前置：**样本有哪些保护，当前能看到什么？
2. **分析面：**代码、数据或行为位于哪一层？
3. **分析目标：**要确认的安全影响是什么？
4. **分析方法：**用静态、动态，还是两者结合来验证？

下面逐项解释 map 中的节点，并指出它们在本清单中的展开位置。

### 1.1 前置：防护识别与对抗

这一支描述分析开始前的样本状态和应用保护，不是漏洞类型，也不代表保护一定有效。

| map 节点 | 含义 | 后续看哪里 |
| --- | --- | --- |
| 查壳：无壳 / 有壳 / 混合 | 判断 APK 是否经过代码保护，以及保护覆盖哪些部分。混合保护可能只处理部分 DEX 或 Native 代码。 | [准备与样本基线](#21-准备与样本基线)、[Native / SO](#225-native--so) |
| 脱壳状态：已脱 / 未脱 / 部分脱 | 描述当前样本可见代码的状态。它与“有没有壳”不是同一件事：有壳样本可以尚未处理、已处理或只处理一部分。 | [准备与样本基线](#21-准备与样本基线)、[工具按用途选择](#42-工具按用途选择) |
| 反调试 / 反 Hook / 反 Root / 模拟器检测 | 应用对运行环境或分析环境的检查。记录触发条件、影响和误报，不因检测存在就认定应用安全或存在漏洞。 | [环境与完整性保护](#235-环境与完整性保护) |
| 完整性校验 / 签名校验 | 用于判断包或运行状态是否符合预期。检查校验覆盖范围、失败时的处理，以及服务端是否仍独立验证关键授权。 | [环境与完整性保护](#235-环境与完整性保护)、[信任边界原则](#244-信任边界原则) |
| SSL Pinning | 客户端对服务端证书或公钥增加约束，属于通信保护配置。需要与 TLS 证书校验、域名校验和服务端配置一起评估。 | [网络观察](#234-网络观察)、[接口与协议](#241-接口与协议) |

### 1.2 分析面

“分析面”回答的是**去哪里找代码、数据和决策**。同一个目标可能跨越多个分析面，例如密钥使用可能从 Java 入口进入 JNI，再参与网络签名。

| map 节点 | 主要检查内容 | 对应章节 |
| --- | --- | --- |
| Java / Smali | Activity、业务调用链、本地校验、网络调用、加密 API、反射与动态加载。 | [Java / Kotlin 与 Smali](#222-java--kotlin-与-smali) |
| Native / SO | JNI 边界、Native 算法、文件和网络操作、内存安全及第三方库。 | [Native / SO](#225-native--so) |
| 资源 / 存储 / 日志 | Manifest、资源文件、配置、数据库、偏好设置、缓存、备份和日志。 | [资源、配置与本地数据](#223-资源配置与本地数据) |
| 网络 / 协议 / 证书 | 请求响应、身份凭据、签名与加密、TLS 配置、证书和重放防护。 | [网络观察](#234-网络观察)、[通信与服务端交互](#24-通信与服务端交互) |
| 组件 / IPC / WebView | Activity、Service、Receiver、Provider、Intent、深链、文件分享和 JavaScript 桥。 | [包信息与 Manifest](#221-包信息与-manifest)、[WebView、组件与第三方 SDK](#226-webview组件与第三方-sdk) |
| 系统 / 内核 | 这是 `android map.txt` 里超出目标 APK 范围的分支。目标 APK 对系统 API 的调用可以作为应用行为分析；Framework、驱动或内核本身的缺陷需要另做平台级分析，不能由 APK 检查直接推出。 | [范围边界](#3-当前-map-的范围边界与扩展方向) |

**对原始 map 的建议：**将“系统 / 内核”移出目标 APK 的核心分析树，或明确标记为“平台级 / 范围外”。APK 使用系统 API 的行为仍然可以分析，但系统组件自身的漏洞应另建平台级分析地图。

### 1.3 分析目标

这部分列出希望确认的安全结果，但 map 中有些项目是结果，有些是分析过程或辅助条件。不要把它们当成同一种“漏洞类型”。

#### 1.3.1 本地验证篡改

指本地注册码、会员状态、功能开关、许可证或环境判断由客户端作出，分析关注这些结果是否只改变本地界面，还是错误地决定了重要业务权限。Root、模拟器、Frida 和调试检测属于被检查的环境条件；完整性或签名检查属于保护措施。

重要结论是：如果样本完全离线，准确说法是“验证逻辑只在本地，没有服务端参与”，而不是“服务端漏验”。如果业务有服务端，继续确认服务端是否会独立校验授权。详见[验证逻辑：本地、服务端与混合](#25-验证逻辑本地服务端与混合)。

#### 1.3.2 数据窃取 / 数据暴露

map 按数据经过的位置分支。这些分支帮助找泄露面，最终要报告的是未经授权的数据暴露及其影响：

| map 子项 | 解释与评估重点 |
| --- | --- |
| 本地数据 | SharedPreferences、数据库、文件、外部存储、备份、剪贴板或截图中是否保存了敏感数据；确认读取权限、保存周期和登出后的清理。 |
| 网络数据 | 请求和响应是否暴露凭据或个人信息，传输保护及证书校验是否正确。抓包只是观察方法，明文或权限缺失才可能构成风险。 |
| 内存数据 | 敏感数据在运行时是否不必要地长期存在、是否进入日志或可被不可信组件访问。内存观察应限于授权样本和测试数据。 |
| IPC 数据 | Provider、广播、Service、Intent 等跨组件边界是否泄露数据或缺少调用方授权。 |
| 侧信道 | 时间、功耗、缓存等间接信号是否可能泄露敏感信息；通常需要特定硬件与实验条件，不能仅凭 APK 静态代码确认。 |

“数据窃取”描述的是结果；“数据泄露”是风险或缺陷；抓包、内存分析和 IPC 检查则是分析手段。

#### 1.3.3 协议逆向与伪造

map 把“协议逆向”和“协议伪造”并列，是为了表达一条分析链，但概念上应拆开：**协议逆向是理解过程，伪造或重放是需要在授权测试中验证的安全结果。**

- **传输层：**识别 HTTP(S)、WebSocket、gRPC 或自定义传输，以及请求和响应格式。
- **认证与授权：**理解 Cookie、Session、Token、JWT、OAuth 或双向认证在系统中的职责；认证成功不等于有权访问任意资源。
- **签名与加密：**判断签名、哈希、HMAC、AES 或 RSA 用于什么安全属性；Base64 / Hex 只是编码形式。
- **防重放：**检查时间戳、Nonce、序列号或一次性凭据是否由服务端验证并正确绑定到操作。
- **通信保护：**检查 TLS、证书校验、Pinning、代理配置和请求完整性控制。

分析目标是确认服务端能否拒绝不符合授权、完整性或时效要求的请求。不要把理解客户端算法或发现 Pinning 本身当成漏洞结论；关键是服务端最终执行了什么授权检查。详见[通信与服务端交互](#24-通信与服务端交互)。

#### 1.3.4 服务端攻击

这一支关注 API 或服务端业务自身的缺陷，客户端逆向只是可能的前置分析来源，并不意味着问题一定在 APK。map 中的各项可这样理解：

- **协议伪造 / 重放：**检验服务端对请求身份、完整性、时效和幂等性的验证。
- **越权：**检验每次资源访问是否验证当前用户对该对象或操作的权限。
- **注入：**检查服务端是否把不可信输入安全地交给数据库、模板、命令或其他解释器。
- **逻辑漏洞：**检查业务状态、价格、额度、角色和流程是否由服务端可信地计算与转换。
- **并发 / DoS：**前者检查并发操作下状态一致性；后者可能影响服务可用性，只能按授权计划在隔离环境评估。
- **风控：**检查服务端风险判断、限流和审计是否作为纵深措施，并避免将风控当成身份授权的替代品。

#### 1.3.5 风控绕过

map 列出的设备、环境、客户端、网络、行为和服务端风控，是**防守方可能采集的风险信号类别**。对于安全评估，应记录哪些信号影响决策、是否会误伤正常用户、是否泄露过多设备信息，以及服务端是否结合账号和业务上下文判断。

其中 Root / 模拟器 / Hook、设备标识、代理、IP、TLS 指纹、请求频率、操作路径和传感器信号都可能随系统版本、权限和设备而变化；单个信号不应作为授权依据。这个节点描述防守机制及其评估范围，不是要求伪造设备身份、规避限流或自动化批量请求。详见[环境与完整性保护](#235-环境与完整性保护)和[业务逻辑与并发](#243-业务逻辑与并发)。

#### 1.3.6 风控绕过手段

map 的下一棵树把可能的规避方式按客户端、设备、网络、行为和服务端对抗分组。理解这棵树的目的，是知道风控面覆盖哪些信号；做防守评估时，应把每一项翻译成“系统如何发现异常、误报如何处理、服务端如何保护关键操作”：

| map 分支 | 防守侧应解释的问题 |
| --- | --- |
| 客户端检测 | Root、调试、插桩或完整性异常只是风险信号时，服务端是否仍独立做认证和授权？正常开发、无障碍和企业设备会不会被误判？ |
| 设备指纹 | 设备标识是否必要、最小化和透明？信号变化或缺失时，系统是否安全降级，而非直接授予或永久拒绝关键权限？ |
| 网络层 | IP、TLS 特征和请求节奏如何参与风险判断？是否有合理限流、异常告警和隐私保护？ |
| 行为层 | 点击、操作路径和传感器信号是否只作为辅助判断？能否通过服务端状态校验、幂等和业务规则阻止重复或越权操作？ |
| 服务端对抗 | 规则、挑战、限流、账号保护和审计是否协同？是否避免把 CAPTCHA 或单一设备信号当成唯一防线？ |

像改机、代理池、验证码代答和分布式请求这样的条目，是威胁建模中的对手能力示例，不是本清单的操作教程。实际测试应使用批准的测试账号、流量和环境，重点验证防御是否有效、可观测且不影响正常用户。

#### 1.3.7 漏洞挖掘

“漏洞挖掘”更准确地说是**发现与验证过程**，不和“数据暴露”“越权”等影响结果处于同一分类层。map 的子项是常见检查面：

- **组件漏洞：**导出组件、Intent 重定向、权限检查、Provider 查询和路径处理。
- **WebView 漏洞：**JavaScript 桥、URL / 来源校验、文件访问和跨域边界。
- **文件与存储：**外部存储、路径规范化、备份、日志和符号链接等文件边界。
- **网络与协议：**明文、证书校验、请求完整性、防重放和对象授权。
- **Native / SO：**内存破坏、整数边界、格式化字符串、命令调用和反序列化。
- **系统与内核：**这属于 Android 平台级漏洞研究，不是当前“目标 APK 分析 map”的挖掘对象。APK 可以暴露它如何调用系统 API，但若要判断 Framework、驱动或内核漏洞，必须另设平台级分析对象和证据。
- **业务逻辑：**越权、状态竞争、并发、支付计算和风控判断。

发现候选点后要继续验证输入是否可控、代码路径是否可达、受影响版本和实际安全影响；仅看到危险 API 或配置不够构成漏洞结论。

### 1.4 分析方法：静态与动态

这是 map 的方法轴，可以套用到任意分析面和目标上；不是“本地分析”与“服务端分析”的专属分支。

| 方法 | 看什么 | 适合回答的问题 | 局限 |
| --- | --- | --- | --- |
| 静态分析 | Manifest、反编译代码、Smali、资源、Native 库、配置和依赖 | 入口在哪里？数据如何流动？判断逻辑可能在哪里？ | 可能受混淆、加固、动态加载和运行时配置影响；静态结果需要验证。 |
| 动态分析 | 运行时调用、文件、日志、组件交互、请求响应和状态变化 | 代码是否实际执行？输入输出是什么？服务端如何响应？ | 只覆盖已运行路径；环境、账号、版本和服务端状态会影响结果。 |

协议分析不是与静态、动态互斥的第三种“运行模式”：它通常先用静态分析定位协议实现，再通过动态观察核对实际请求和响应。实际评估常常是静态定位、动态验证、结合服务端证据得出结论。

### 1.5 把 map 节点串成一条分析路径

以下例子展示同一个问题如何跨越 map 的多个分支：

| 问题 | 前置 / 保护 | 分析面 | 目标 | 方法 |
| --- | --- | --- | --- | --- |
| README 中的本地注册码示例 | 通常无服务端保护参与 | Java / Smali、本地界面 | 本地验证仅影响客户端状态 | 静态看条件分支，动态确认结果；结论是教学样本的本地校验边界，不是服务端漏洞 |
| 登录后某资源访问控制 | 可能有签名、Token 或风控 | Java / Native、网络 / 协议、服务端 API | 认证、授权及业务状态是否正确 | 静态追踪客户端请求构造，动态观察测试环境请求，再核对服务端授权结果 |
| Provider 返回敏感记录 | 组件权限或导出配置 | Manifest、Provider、数据存储 / IPC | 未授权数据是否可读 | 静态检查配置和访问代码，动态验证不同授权状态下的返回结果 |
| Native 输入处理异常 | 可能有混淆或完整性保护 | Java/JNI 边界、Native / SO | 输入校验与内存安全 | 静态追踪边界，使用隔离测试输入动态验证影响 |

所以 map 本身可以保留为总览，但阅读时应给每个条目补上“分析面 / 目标 / 方法”标签，避免误以为树上的兄弟节点都是同一类事物。

## 2. APK 分析流程与检查清单

### 2.1 准备与样本基线

#### 2.1.1 明确测试范围

- 记录授权范围、应用包名、版本、测试账号和允许触达的接口。
- 优先使用隔离的测试设备、测试环境和虚构数据。
- 不对生产账号、真实用户数据或未授权服务做批量请求和破坏性验证。
- 记录每个结论对应的应用版本、系统版本、设备类型和复现条件。

#### 2.1.2 保存样本信息

- APK 文件名、来源、文件大小和 SHA-256。
- 包名、版本号、最低与目标 Android API、签名证书信息。
- APK 包含的 ABI：例如 `arm64-v8a`、`armeabi-v7a`、`x86_64`。
- 是否包含 split APK、动态特性模块或额外下载的代码与资源。
- 安装、启动、登录和主要功能是否正常；先保留未修改样本。

#### 2.1.3 识别保护与运行条件

- 查看 DEX 数量、Native 库、资源目录和启动 Application 类。
- 留意代码混淆、字符串加密、动态加载、壳或虚拟化保护的迹象。
- 记录 Root、模拟器、调试器、代理或设备完整性要求是否影响正常运行。
- 将“发现保护机制”与“发现安全漏洞”分开记录；有保护不等于业务逻辑安全。

**小白检查点：**先确认样本能否安装和正常运行，记录原始状态，再开始分析。不要一开始就修改 APK，否则难以分辨是样本行为还是修改造成的问题。

### 2.2 静态分析：不运行 APK，检查包内结构与代码

#### 2.2.1 包信息与 Manifest

查看：

- 包名、版本、SDK 配置、应用入口、启动 Activity。
- 权限声明及权限使用位置，特别是短信、通讯录、位置、麦克风、相机和无障碍权限。
- `application` 属性：`debuggable`、`allowBackup`、`usesCleartextTraffic`、`networkSecurityConfig`。
- `activity`、`service`、`receiver`、`provider` 的 `exported`、`permission`、`intent-filter`、`authorities`。
- 深链和 App Link 的 scheme、host、path 匹配规则。
- FileProvider 的路径配置和对外分享范围。

**小白检查点：**导出的组件和深链是需要进一步审查的入口，不单凭 `exported` 就判定漏洞。还要确认外部调用能否触发敏感操作、读取数据，代码里是否有可靠的权限和身份校验。部分属性的默认值会随 Android 版本和 `targetSdkVersion` 改变。

#### 2.2.2 Java / Kotlin 与 Smali

从应用入口和关键业务流程向下追踪调用链：

- 入口：`Application`、启动页、登录页、支付或授权相关页面。
- 网络：OkHttp、Retrofit、Volley、`HttpURLConnection` 或自定义客户端。
- 身份与权限：登录状态、角色、用户 ID、会员状态、功能开关和授权判断。
- 校验逻辑：`check`、`verify`、`validate`、`isAuthorized` 等方法及其调用方。
- 加密 API：`Cipher`、`MessageDigest`、`Mac`、`Signature`、`KeyStore`。
- 反射和动态加载：`Class.forName`、`DexClassLoader`、`PathClassLoader`。
- 序列化、WebView 桥接、文件处理和组件间调用。

**小白检查点：**搜索错误提示、接口路径、配置键和方法名可以帮助定位入口；找到可疑方法后继续看调用方、输入来源、返回值如何影响业务，避免只凭一个字符串下结论。

#### 2.2.3 资源、配置与本地数据

检查以下位置是否包含敏感信息或不安全配置：

- `res/values/strings.xml`、`res/raw/`、`assets/`、`BuildConfig` 和打包配置。
- SharedPreferences、DataStore、SQLite / Room、Realm、内部文件和外部存储。
- 日志、崩溃报告、剪贴板、截图、通知、缓存和备份配置。
- Token、个人信息、调试开关、测试账号、内部 URL、证书和密钥材料。
- 文件权限、文件共享路径、临时文件清理和导出行为。

**小白检查点：**发现某字段写入本地不等于漏洞。需要判断它是否敏感、是否明文、其他应用或备份能否读取、数据保存多久，以及应用是否在退出或登出后清理。

#### 2.2.4 密钥、密码学与签名设计

区分“算法使用是否正确”和“密钥管理是否安全”：

- 识别哈希、消息认证码、对称加密、非对称加密和数字签名的用途。
- 检查密钥是否硬编码、复用、随 APK 一起分发，或被写入日志和配置。
- 检查随机数、Nonce、初始化向量、密钥长度、模式和认证标签使用方式。
- 查看 Android Keystore 的使用边界、密钥用途和失效策略。
- 检查签名是否覆盖关键请求字段，以及服务端是否重新验证业务权限。

**小白检查点：**Base64 是编码，不是加密。把密钥放进 Native 库、混淆代码或字符串加密中，不能让随客户端分发的固定密钥变成真正的服务端秘密。Keystore 可以加强密钥保存，但不能阻止已被控制的运行环境调用应用本来有权使用的密钥操作。

#### 2.2.5 Native / SO

检查 `lib/<ABI>/` 下的共享库和 Java/Kotlin 到 Native 的调用关系：

- 导出符号、字符串、JNI 方法、`JNI_OnLoad` 和 `RegisterNatives`。
- Native 中的网络、密码学、授权判断、文件操作和命令执行逻辑。
- 不同 ABI 是否存在行为差异或遗漏保护。
- 内存安全风险：越界访问、整数溢出、格式化字符串、释放后使用和不安全反序列化。
- 第三方 Native 依赖的版本、来源和已知风险。

**小白检查点：**Java 层找不到关键逻辑时，再沿 JNI 调用边界检查 Native 库。反汇编结果需要结合交叉引用、运行时行为和输入输出验证，不能只根据函数名判断用途。

#### 2.2.6 WebView、组件与第三方 SDK

- WebView：JavaScript 是否必要；桥接方法是否过宽；加载的 URL、文件访问和来源限制是否明确。
- Intent：深链参数是否经过校验；是否可能把不可信 Intent 转发到敏感组件。
- ContentProvider：读写权限、路径限制、查询参数和返回数据是否受控。
- 第三方 SDK：采集哪些数据、何时上传、是否复用权限、是否带有过时依赖。
- 动态模块：代码来源、完整性和加载失败时的安全行为。

**小白检查点：**关注“外部输入如何到达敏感操作”。仅发现 `addJavascriptInterface`、Provider 或深链并不足以证明漏洞，还要确认可达性、版本条件、权限和实际影响。

### 2.3 动态分析：在授权环境观察运行时行为

#### 2.3.1 建立可重复的运行基线

- 使用专用模拟器或测试设备，记录 Android 版本、ABI、Root 状态和网络环境。
- 使用测试账号完成登录、登出、密码重置和关键业务流程。
- 对照正常与异常输入，记录界面、日志、文件和网络行为的差异。
- 保存时间、步骤、输入和观察结果，保证之后能重复验证。

#### 2.3.2 运行时调用与决策点

- 观察关键校验方法的输入、输出和调用时机。
- 对照静态代码检查实际执行分支，识别远程配置、动态代码和服务端响应的影响。
- 观察密钥或 Token 在运行时的使用位置，避免将测试数据写入报告或共享日志。
- 检查登录、登出、权限变化和会话过期后的状态清理。

可在自有应用或授权样本上使用调试器、插桩或 Hook 工具辅助观察；重点是确认数据流和安全边界，而不是把工具本身的输出当成漏洞结论。

#### 2.3.3 文件、日志和进程间通信

- 检查运行后新增或修改的文件、数据库、偏好设置和缓存。
- 查看敏感数据是否进入 Logcat、崩溃报告、剪贴板、通知或临时文件。
- 测试导出组件在无权限、低权限和未登录状态下的访问控制。
- 确认文件共享 URI、Provider 查询和广播数据是否遵守最小权限。

#### 2.3.4 网络观察

- 记录请求和响应的主机、路径、方法、状态码、字段类型和调用功能。
- 检查 HTTPS、证书校验、明文流量例外、重定向和域名配置。
- 观察 Token 的签发、刷新、过期、登出失效和权限变化。
- 检查敏感数据是否出现在 URL、请求头、响应、错误信息或日志中。
- 对签名和加密流程记录输入、输出和调用位置；不要在文档中保存真实密钥或用户凭证。

**小白检查点：**抓不到流量时先检查测试环境和应用网络配置，并在授权范围内按项目测试方案处理。不要通过拦截真实用户流量或扩大请求规模来解决问题。

#### 2.3.5 环境与完整性保护

记录应用对调试器、Root、模拟器、签名变化、代理、设备完整性或运行环境异常的响应：

- 触发条件、检测位置、用户可见行为和服务端是否参与判断。
- 检测失败是关闭敏感功能、要求重新认证，还是只影响非关键 UI。
- 防护是否误伤正常用户，是否存在无障碍、企业设备和兼容性影响。
- 关键授权是否仍由服务端执行，而不是依赖客户端环境检测结果。

这里的评估重点是防护边界、可用性和服务端兜底，不把保护机制的绕过过程作为本清单的操作步骤。

### 2.4 通信与服务端交互

#### 2.4.1 接口与协议

- 列出业务功能对应的接口和数据类型，标记匿名、登录后和高风险操作。
- 识别 HTTP(S)、WebSocket、gRPC、自定义 TCP/UDP 等传输方式。
- 检查请求字段、响应字段、错误处理、分页和版本兼容行为。
- 检查请求签名、时间戳、Nonce、序列号和服务端防重放策略。

#### 2.4.2 身份认证与授权

- 登录认证与资源授权是否分开验证。
- 服务端是否根据当前会话重新确认用户身份、角色和资源所有权。
- Token 是否有明确有效期、作用范围、撤销机制和安全传输方式。
- 对象 ID、角色、金额、状态等关键字段是否由服务端决定或校验。
- 登出、账号封禁、权限变更后，旧会话是否按设计失效。

#### 2.4.3 业务逻辑与并发

在测试环境和测试数据中检查：

- 重复提交、状态跳转、优惠或额度计算是否保持一致。
- 关键操作能否被跳过步骤、重复执行或在并发请求下产生不一致状态。
- 服务端是否执行限流、幂等控制、审计和异常告警。
- 负面测试是否可能影响真实业务；有风险时停止并采用隔离环境复现。

#### 2.4.4 信任边界原则

- 客户端输入、客户端显示状态和客户端计算结果都可以被用户控制。
- 客户端可以做体验性检查，但价格、权限、账户归属、额度和最终状态应由服务端权威校验。
- 客户端内置的共享秘密不能作为唯一的服务端身份凭据。
- 设备完整性或风险评分可以作为信号，不应替代账号、资源和业务权限验证。

### 2.5 验证逻辑：本地、服务端与混合

| 类型 | 典型结构 | 分析重点 | 常见误区 |
| --- | --- | --- | --- |
| 本地验证 | 应用在设备上完成判断，没有服务端参与 | 判断逻辑是否只影响 UI，数据或授权是否完全依赖客户端 | 把它描述成“服务端漏验”；纯本地样本可能根本没有服务端 |
| 服务端验证 | 客户端提交请求，服务端作出最终决定 | 服务端认证、授权、状态校验、Token 生命周期和审计 | 认为隐藏或混淆客户端代码就能替代服务端校验 |
| 混合验证 | 客户端预检查，服务端再次确认 | 找出真正的最终裁决点，并确认客户端结果不能直接授权 | 把客户端成功提示当作服务端已接受业务结果 |

**分析问题：**这个判断在哪里发生？它使用了哪些输入？结果由谁保存？客户端是否能单方面改变最终状态？服务端是否对每次敏感操作重新授权？

### 2.6 漏洞与风险分类索引

以下是按风险对象整理的索引。一个问题可以同时带有多个标签，例如“动态验证、客户端、认证授权”。

| 风险对象 | 检查项示例 |
| --- | --- |
| 组件与 IPC | 组件暴露、权限不足、深链参数未校验、Intent 转发、Provider 越权读取 |
| 本地数据 | 敏感数据明文保存、日志泄露、备份暴露、外部存储访问过宽、登出后残留 |
| 密钥与密码学 | 固定密钥随包分发、弱随机数、不安全模式、密钥复用、签名字段覆盖不足 |
| 网络通信 | 明文传输、证书校验错误、Token 泄露、敏感字段进入 URL、错误处理泄露信息 |
| WebView | 不必要的 JavaScript 桥、来源校验不足、文件访问范围过宽、不可信 URL 加载 |
| Native | 内存安全缺陷、不安全反序列化、边界检查遗漏、依赖组件风险 |
| 服务端授权 | 对象级越权、角色校验缺失、会话失效不及时、客户端字段被当作可信依据 |
| 业务逻辑 | 状态机不一致、重复操作、并发竞争、金额或额度计算错误 |
| 隐私与数据治理 | 超范围采集、用途不透明、保存过久、第三方 SDK 过度采集 |

## 3. 当前 map 的范围边界与扩展方向

当前 map 用来分析目标 APK。它可以解释应用如何使用 Android 能力、如何存取和发送数据，以及应用自身的配置、校验和业务逻辑是否安全。它不能单独证明 Android 系统组件存在漏洞。

以 NFC 为例：如果 APK 通过正常系统 API 使用 NFC，分析可以追踪 APK 请求了什么权限、调用了什么功能、如何处理和发送数据；若怀疑 NFC Framework、驱动或硬件实现本身有缺陷，则应把研究对象改为相应系统组件，并使用匹配的 Android 版本、系统映像和独立的平台级方法。

其他安全方向可以作为后续独立地图，不应混进当前目标 APK 分类：

- **DEX / Smali 与运行时：**字节码、类加载、ART、调试和运行时行为分析。
- **Native 与二进制安全：**ARM64、JNI、ELF、反汇编、内存安全和模糊测试。
- **加固与代码保护评估：**混淆、动态加载、虚拟化保护、完整性与供应链风险。
- **移动通信安全：**认证协议、令牌生命周期、加密设计和服务端授权模型。
- **iOS 安全：**Mach-O、Objective-C / Swift、代码签名、Keychain 和运行时分析。
- **恶意软件分析：**样本行为、持久化、通信、家族归类和防御检测。
- **固件与 IoT：**固件文件系统、启动链、硬件接口、更新签名和设备通信协议。
- **漏洞研究：**组件、Native 库、内核和业务逻辑缺陷的发现、验证与修复。

这些方向需要不同的操作系统、编译原理、计算机体系结构、汇编、网络和密码学基础；不必一开始全部学习，先选一个方向完成从发现到修复验证的闭环。

## 4. 学习路线、工具与自查清单

### 4.1 小白学习顺序

1. 补 Android 基础：组件、Manifest、权限、生命周期、存储和网络请求。
2. 学会看 APK 结构、Java / Kotlin 反编译结果和基础 Smali 控制流。
3. 按一条业务流程做静态追踪：入口、输入、校验、网络调用、结果展示。
4. 在自有教学 App 上做动态观察，记录文件、日志、组件调用和请求响应。
5. 学习 Android 密码学 API、Keystore、TLS、Token 和服务端授权原则。
6. 再进入 JNI、ELF、ARM64 和 Native 调试；需要时学习加固和运行时保护评估。
7. 每次练习都写简短报告：影响、证据、复现条件、修复建议和回归结果。

## 5. 案例模式：把分类应用到问题上

下面是用于理解分析路径的通用模式，不指向未核实的厂商事件或特定漏洞编号。

### 5.1 纯本地注册码判断

应用在本机比较输入值并决定是否显示“成功”。检查点是注册码是否只影响本地状态、修改客户端状态后是否仍有任何服务端授权。它说明客户端不能独自承担重要权限裁决。`gnaixx/droid-hack` README 中的 Smali 条件跳转示例属于这种教学型切片；它没有证明某个服务端漏洞。

### 5.2 客户端签名请求与服务端授权

检查客户端如何构造请求、服务端验证哪些字段、Token 如何失效、资源所有权如何确认。报告应聚焦服务端是否可信地完成身份认证、对象授权和状态校验；不要把“能复现客户端算法”本身当成越权结论。

### 5.3 导出组件访问敏感数据

从 Manifest 找到候选入口，在测试设备上确认外部调用条件、权限检查、可返回的数据和影响版本。修复通常包括收紧导出范围、要求适当权限、校验调用方和限制返回内容。

### 5.4 Native 库中的关键校验

从 Java/JNI 边界确定数据如何传入 Native、结果如何返回，再检查边界校验、密钥使用和授权逻辑。对于内存安全问题，应在隔离环境验证影响并给出受影响版本与修复建议。

### 5.5 SuperCard X 类 NFC 恶意 APK

按报道描述，目标 APK 是 Reader / Tapper 恶意应用。map 可以用于分析 Reader 如何申请并使用 NFC 能力、数据如何在进程内流动、是否落盘，以及应用如何通过网络与 C2 通信；也可以分析 Tapper 的权限、通信和运行行为。这属于**目标 APK 的行为与数据流分析**，不等于发现 Android 系统漏洞。

仅凭报道不能确定卡片交互究竟是静态数据采集、实时中继还是两者结合，也不能证明 NFC 系统实现存在缺陷。要区分这些情况，需要取得样本并在授权、隔离的实验环境中验证；报道中“低检出率”及具体交易能力也应视为待核实信息。

## 6. 报告模板

每个发现至少记录：

1. **标题与风险等级：**简明描述问题和影响对象。
2. **环境：**应用版本、系统版本、设备、账号类型和测试环境。
3. **前置条件：**所需权限、登录状态、用户交互和配置。
4. **复现摘要：**最少且可重复的步骤；使用测试数据，不附真实凭证。
5. **证据：**相关配置、调用链、请求响应或日志片段，并移除个人信息和密钥。
6. **影响：**可访问或修改的数据、受影响用户、业务边界和实际限制。
7. **根因与修复：**服务端校验、组件权限、数据保护或代码修复建议。
8. **回归验证：**说明修复后如何确认问题消失且功能仍正常。

## 8. 一句话总结

APK 分析的主线是追踪数据与决策从哪里来、经过哪些组件、最终由客户端还是服务端裁决；静态 / 动态是方法，数据 / 密钥 / 算法是检查对象，本地 / 服务端是信任边界。把这三类标注分开，小白更容易按清单检查，也不容易把“发现机制”“分析方法”和“安全结果”混为一谈。
